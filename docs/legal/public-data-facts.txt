1. ONE FINDING TO FIX BEFORE THE DOCUMENTS ARE WRITTEN
--------------------------------------------------------------------------------

THE BETA-ACCESS FORM STORES THE SUBMITTER'S RAW IP ADDRESS.

Every authentication path hashes the IP before storing it (keyedHash in
auth.ts). The beta-access route is the single exception: it passes ip(req)
straight into consumeRateLimit, and the value lands in a column named
"key_hash" which, on this one path only, holds no hash.

So today, submitting that form writes: an email address, an optional free-text
note, and a raw IP address, kept indefinitely.

It is a one-line fix. It should be made BEFORE these documents are written, so
the policy describes the code we want rather than the code we have.

2. SHAPE OF THE THING
--------------------------------------------------------------------------------

- TWO SEPARATE DEPLOYMENTS. The public service has its own Postgres database,
  its own cookies, its own secrets and its own codebase. It shares no database,
  session or credential with the private portal. The private portal is not in
  scope for these documents.

- THERE IS NO PUBLIC SIGN-UP. Accounts exist only because an operator ran a
  command-line tool (`admit`). A visitor cannot create one. Admission is by
  invitation following a beta-access request.

- THE DEMO TOUCHES NOTHING. It runs entirely from memory in the browser tab:
  no account, no cookie, no server request, no stored data. Leaving the page is
  the reset. Every figure in it is fabricated.

- EVERY ROUTE RESOLVES THE ACCOUNT FROM THE SESSION. No endpoint accepts a
  "whose data" parameter. An id the caller does not own answers 404, not 403.

- NO PAYMENT DATA ANYWHERE. No billing, no card, no bank details, in any table.
  Nothing is sold. There are no plans, tiers or subscriptions.

3. WHAT IS STORED ABOUT A PERSON — IDENTITY AND AUTHENTICATION
--------------------------------------------------------------------------------

public_accounts
    Email address (unique), password hash (scrypt), display name, a
    forced-password-change flag and its expiry, a disabled flag, when the
    password last changed, when the account was created.
    NO real name, postal address, phone number, date of birth or payment data.

public_sessions
    A SHA-256 hash of the session token — never the token itself — plus account
    id, expiry, revocation time, created time.
    Session lifetime: 12 hours.

public_trusted_devices
    Hash of the "remember this device" token, account id, expiry, revocation.
    Lifetime: 30 days.

public_auth_challenges
    Hash of the emailed six-digit sign-in code, expiry, attempt count, whether
    consumed.
    Lifetime: 10 minutes. Single use.

public_recovery_events
    Account id, expiry, whether consumed. No password is ever stored in plain
    text at any point.

public_audit_events
    Event name, account id (set to NULL if the account is deleted), a JSON
    metadata field (currently written empty), timestamp.
    Events recorded: beta-access requested; sign-in code created; sign-in code
    verified; login failed; password changed; recovery requested; recovery
    issued; trusted device used.

public_rate_limits
    Bucket name, key hash, window start, count.
    Authentication paths store an HMAC of the IP address.
    The beta-access path stores the RAW IP address — see section 1.

public_early_access_requests
    Email address, optional free-text note (up to 1,000 characters), status,
    source, created timestamp, handled timestamp.
    No expiry and no deletion process exists today.

5. COOKIES AND BROWSER STORAGE
--------------------------------------------------------------------------------

TWO COOKIES, BOTH STRICTLY FUNCTIONAL:
    vts_public_session_v1          12 hours
    vts_public_trusted_device_v1   30 days
Both are HttpOnly, Secure, SameSite=Strict and path-scoped. Both hold a random
token; the server stores only its hash.

NO analytics, advertising or tracking cookie of any kind.

LOCAL STORAGE is used for device-local convenience only — a remembered view
choice on the trade log, drafts in the study wizard, which sample study games
are in the user's list. It stays on the device and is never sent to the server.

7. DELETION AND RETENTION — THE HONEST CURRENT STATE
--------------------------------------------------------------------------------

REVISED. Everything in the old section 7 has changed. Read this version.

7.1  ACCOUNT DELETION IS BUILT AND LIVE.
     Settings carries a delete control. It warns, the person confirms, and a
     link is emailed. The link is valid ONE HOUR and works ONCE; ignoring it
     cancels the request and nothing happens. Confirming deletes the account
     immediately, in one database transaction, with NO grace period.
     - 26 tables carry "on delete cascade", so the account row going takes the
       user's records with it by database action rather than by application
       code remembering to.
     - The matching beta-access request is deleted too, by email address —
       it is the one row about the person that no cascade can reach.
     - A final confirmation email is sent, and nothing about the address is
       kept afterwards. There is no suppression list, so the same address can
       be admitted again later. Keeping an address in order to block it would
       not be deletion.
     - No "deactivate instead" alternative is offered anywhere.
     Verified against a real Postgres database by counting the rows in every
     table carrying an account id, before and after.

7.2  RETENTION PERIODS ARE ENFORCED BY A SCHEDULED SWEEP.
     A job runs when the service starts and every six hours after that. It
     deletes:
     - BETA-ACCESS REQUESTS — 180 days (six months) after the request was made.
       A repeat submission from the same address restamps that clock, because
       asking again is asking again rather than running out.
     - EXPIRED OR SPENT AUTHENTICATION ROWS — an expired or signed-out session,
       an expired or used sign-in code, an expired or rotated trusted-device
       token, and a spent or expired account-deletion link.
     - RATE-LIMIT COUNTERS whose window started more than 24 hours ago. Those
       rows hold a keyed hash of an address and a count, nothing else.
     Only EXPIRED OR SPENT rows, never merely old ones: a live session and a
     browser the person asked us to remember are untouched.

7.3  A BETA-ACCESS REQUEST ENDS AT THE EARLIEST OF THREE THINGS.
     - The person is ADMITTED. The row is deleted as part of admitting them.
     - The person ASKS. Deleting an account takes the request row with it.
     - 180 DAYS pass. The sweep takes it.

7.4  AUDIT ROWS ARE THE ONE INTENTIONALLY RETAINED TABLE, and they outlive the
     account by design: deleting an account sets their account id to NULL
     rather than removing the row. An audit row holds an event name, an
     account id where applicable, a timestamp, and a metadata field.
     CORRECTED IN THIS REVISION — the metadata is no longer a single value.
     Two events write it: whether a trusted device was requested at sign-in,
     and which document versions were accepted at the clickwrap (as a list of
     "document@version" strings, e.g. "terms@2026-08-28.1"). Everything else
     writes an empty object. No address, no token, no content.
     (Recovery events used to be in this category. They are not any more —
     migration 0014 made them cascade with the account, so audit events are
     now the only exception, which is a far simpler thing to disclose.)

9. SECURITY MEASURES WORTH STATING
--------------------------------------------------------------------------------

A policy that claims less than the code does is a wasted opportunity.

- Passwords hashed with scrypt; never stored or logged in plain text.
- EVERY sign-in requires a code emailed to the account's address, valid ten
  minutes, single use, with attempts counted.
- Session and trusted-device tokens are stored only as hashes, so the database
  alone cannot be used to sign in as somebody.
- Rate limiting on sign-in, verification, recovery and the beta-access form.
- Sign-in and recovery answer identically whether or not an account exists, so
  the site cannot be used to discover who has one.
- Cookies are HttpOnly, Secure and SameSite=Strict, and the API refuses a
  non-HTTPS origin outright.
